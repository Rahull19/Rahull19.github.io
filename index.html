01About

I come at AI from the backend.

Treat the model as one unreliable component inside a reliable system.

AlertLens

Alert intelligence for camera-AI alerts

Turns a stream of about 1,500 AI-detected store alerts a day into answers and signals: a chatbot that answers questions in under 2 seconds, scheduled analytics, and an anomaly engine that flags spikes, peer outliers, repeat patterns and silent stores. Only read-only queries ever reach the source data.

  • Python
  • FastAPI
  • MySQL
  • LLM APIs
  • SQL contracts
  • pytest
  • ~1,500alerts a day
  • < 2 schatbot answers
  • 475automated tests
  • 87stores · ~100–120 users

Problem

Camera AI raises roughly 1,500 alerts a day across stores. Operations teams need to question that stream and spot what matters without writing SQL, and without any chance of an AI-generated query changing the source database.

What it does

A chatbot answers questions over the alert data in under 2 seconds. Background analytics run on a schedule, and an anomaly engine flags spikes, peer outliers, repeat patterns and stores that have gone silent.

My contributions

  • Built the AlertLens service in Python and FastAPI.
  • Defined SQL contracts that bound what the model is allowed to ask of the data.
  • Added a read-only parser guard so only SELECT statements can run.
  • Designed scheduled analytics that split light incremental queries from heavy full-table runs.
  • Built the anomaly engine: spikes, peer outliers, repeat patterns, silent stores.
  • Ran it on free-tier LLM API keys and covered it with 475 automated tests.

Architecture

chat path
  1. Question
  2. SQL contract
  3. Read-only parser guard
  4. Alert data (MySQL)
  5. Answer < 2 s
scheduled path
  1. Scheduler
  2. Light queries (recent changes)
  3. Heavy queries (full tables)
  4. Anomaly engine
  5. Insights

Challenges & how I solved them

Letting an LLM query live data safely
Every generated statement passes a parser guard; anything other than a read-only SELECT is rejected before it reaches the database.
Fast answers on free-tier LLM keys
SQL contracts keep the model's job small and predictable, so the chatbot answers in under 2 seconds.
Analytics without hammering the database
Light queries over recent changes run often; heavy full-table queries run separately on the background schedule.

Proprietary codebase. Architecture shared at a high level.

Personal Analyst

Conversational analytics on mobile

Ask a business question in plain language and get numbers back in under 1.5 seconds over millions of records, with every figure traced to its source rows.

  • < 1.5 sresponse time
  • Millionsof records
  • FastAPI
  • ClickHouse
  • sqlglot
  • LLM

Problem

Business users want numbers from a large analytics store on their phones. An assistant that guesses a number is worse than no assistant at all.

What it does

Translates questions into SQL over ClickHouse, runs it inside guardrails, and returns an answer in under 1.5 seconds. A fact-checker ties each reported figure back to the rows it came from.

My contributions

  • Built the Python and FastAPI backend for the mobile assistant.
  • Put generated SQL behind a sqlglot validation guard and a scope-limited CTE.
  • Built the fact-checking stage that traces every figure to its source rows.

Architecture

  1. Question
  2. LLM → SQL
  3. sqlglot guard + scoped CTE
  4. ClickHouse
  5. Fact-checker
  6. Answer < 1.5 s

Challenges & how I solved them

Hallucinated numbers
A fact-checker traces each figure to source rows before the answer is returned.
Unsafe or over-broad SQL
Queries are parsed and validated with sqlglot, and confined by a scope-limited CTE so they only see permitted data.
Latency at scale
Answers in under 1.5 seconds across millions of records.

Proprietary codebase. Architecture shared at a high level.

Store Alerts PWA

Installable mobile app for store managers

Managers review AI-detected camera alerts, resolve them with a mandatory note, and get push notifications, with escalations climbing from store to cluster to regional manager every 5 minutes.

  • 147automated tests
  • 30–40managers · 3 levels
  • FastAPI
  • MySQL
  • JWT
  • Web Push
  • Vanilla JS

Problem

Store managers need to act on camera-AI alerts from their phones, and unresolved alerts need to reach the next level of management quickly, without shipping a native app.

What it does

A mobile-first, installable PWA: managers review alerts, resolve them with a mandatory note, and receive push notifications. An escalation engine moves unresolved alerts up from store to cluster to regional manager.

My contributions

  • Built the whole mobile app myself, backend and frontend, end to end.
  • FastAPI and MySQL backend with JWT authentication scoped to each manager's stores.
  • Vanilla-JavaScript frontend with a service worker and web manifest, with no framework or build step.
  • Encrypted Web Push (VAPID) with a push monitor that batches routine notifications and fast-tracks high-priority ones.
  • Escalation engine every 5 minutes with database-configurable thresholds and idempotent workers.
  • 147 automated tests with pytest and Playwright.

Architecture

data
  1. Camera AI
  2. 5-min sync
  3. MySQL
  4. FastAPI · store-scoped JWT
  5. PWA
escalation
  1. Escalation engine (5 min)
  2. Store → cluster → regional
  3. Push monitor
  4. Web Push (VAPID)

Challenges & how I solved them

Duplicate escalations
Workers are idempotent, so a re-run never escalates or notifies twice.
Notification noise
Routine alerts are batched; high-priority ones go out immediately.
Push on iPhone
iOS only delivers web push to installed apps, so the app guides users through Add to Home Screen.
Who sees what
JWTs are scoped to stores, so each manager only sees alerts they are responsible for.

Proprietary codebase. Architecture shared at a high level.

05Engineering expertise

How I engineer LLM systems.

The principles I keep coming back to, and where each one shows up in shipped work.

Guardrails before generation

A model should never be the last line of defence. Validate and constrain what it produces before it touches real data.

In practicesqlglot validation and scope-limited CTEs in Personal Analyst; a read-only parser guard in AlertLens.

Answers you can trace

If a system reports a number, it should be able to show where the number came from.

In practiceA fact-checking stage that traces every figure back to its source rows.

Humans where mistakes are expensive

Automate the work, not the accountability. Put a person at the irreversible steps.

In practiceApproval gates before build and deploy in Agent Builder; approval before sending in the email agent.

Provider-agnostic LLM layers

Models and vendors change. Business logic shouldn't depend on any one of them, or on it being up.

In practiceA GPT-4 / Claude / Gemini model factory with circuit breakers in NegotiumAI; four-provider extraction in the claims agent.

Measured, not assumed

LLM features get tests and evaluation like any other backend code.

In practice475 tests on AlertLens, 147 on the PWA, and an evaluation harness tracking hallucination rate.

Services with one job each

Split by responsibility, keep I/O asynchronous, and make background work safe to re-run.

In practiceCCTOP split into API, RAG and chatbot services; idempotent escalation workers in the PWA.
